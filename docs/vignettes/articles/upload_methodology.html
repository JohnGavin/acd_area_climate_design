Upload methodology / Methodik der Upload-Suche

How the address-to-ACD lookup works (algorithm, performance, per-fix details)

This page documents how the Upload → ACD tool works internally: algorithm, assumptions, performance numbers, and per-fix details (A/B/C/D). The upload tool itself is at upload.html.

Diese Seite dokumentiert die interne Funktionsweise des Upload → ACD-Werkzeugs: Algorithmus, Annahmen, Leistungskennzahlen und Details zu den einzelnen Verbesserungen (A/B/C/D). Das Upload-Werkzeug selbst befindet sich unter upload.html.

How it works

Algorithm / Algorithmus

This page does not use the project’s spatial join or building-footprint layer. It is a direct address-table lookup against ogdwien:ADRESSENOGD (291,823 registered address points), running in DuckDB-Wasm entirely in your browser. See the Methodology page for the dashboard’s spatial pipeline (different layers, different question).

The join uses three normalised keys:

  • PLZ — four-digit postcode (cast to VARCHAR)
  • Street name — LOWER(TRIM(name_str)) matched against the user column
  • House number — LOWER(TRIM(name_onr)) matched against the user column

Schrebergärten / garden-plot addresses with a / in the street or Parz in the house-number column are split into two lookup attempts automatically.

What this page does NOT do

  • ❌ It does not run the R/join_buildings_zones.R spatial join
  • ❌ It does not return confidence_tier (A–E distance-based labels)
  • ❌ It does not return zone_id or nearest_zone_dist_m for matched buildings
  • ❌ It does not consult the GEBAEUDEINFOOGD building-footprint layer

Spatial enrichment of matched rows with these fields is tracked as a follow-up in issue #42.

Die Verknüpfung verwendet drei normalisierte Schlüssel:

  • PLZ — vierstellige Postleitzahl (als VARCHAR)

When (PLZ, street_norm) matches but the exact house_norm is absent from ADRESSENOGD, the algorithm falls back to the nearest registered house number on the same street. The numeric distance between the user’s house number and the nearest ADRESSENOGD house number is stored in the house_distance column so users can filter low-confidence results. Distance is capped at 20 — rows further than that remain unmatched.

Wenn (PLZ, Straßennorm) übereinstimmt, die exakte Hausnummer aber nicht in ADRESSENOGD enthalten ist, fällt der Algorithmus auf die nächstgelegene registrierte Hausnummer in derselben Straße zurück. Die numerische Distanz zwischen der eingegebenen und der gefundenen Hausnummer wird in der Spalte house_distance gespeichert, damit unsichere Ergebnisse herausgefiltert werden können. Abstände über 20 bleiben als unmatched erhalten.

  • The nearest registered house number on the same street is a reasonable proxy for an unregistered parcel or new building.
  • A numeric distance of ≤ 20 is close enough to be useful; beyond that the result is likely a different building entirely.
  • The user’s house number contains a leading integer (e.g. 21, 21a). If the house number is a parcel code like Parz 38, no leading integer is extracted and the fuzzy pass is skipped.
  • Die nächstgelegene registrierte Hausnummer in derselben Straße ist ein vertretbarer Ersatz für ein nicht registriertes Grundstück oder ein neues Gebäude.
  • Ein numerischer Abstand von ≤ 20 ist nahe genug, um nützlich zu sein; darüber hinaus handelt es sich wahrscheinlich um ein anderes Gebäude.
  • Die Hausnummer des Nutzers enthält eine führende Ganzzahl (z. B. 21, 21a). Ist die Hausnummer ein Parzellen-Code wie Parz 38, wird kein Wert extrahiert und der Fuzzy-Durchlauf übersprungen.

Some Vienna addresses identify corner parcels with two street names joined by /, e.g. Achengasse 4/Lavantgasse 1a. The previous implementation claimed to handle these but the split was not being applied before the main JOIN, so no recovery occurred. Fix B reimplements the splitter in JavaScript before the JOIN: each A/B street is expanded into two sub-rows, each looked up independently. The results are aggregated as acd_b (second match) and match_quality = "split_both" (both matched) or "split_partial" (one matched).

Manche Wiener Adressen bezeichnen Eckgrundstücke mit zwei durch / verbundenen Straßennamen, z. B. Achengasse 4/Lavantgasse 1a. Die frühere Implementierung behauptete, diese zu verarbeiten, aber die Aufteilung fand vor dem JOIN nicht statt. Fix B reimplementiert den Splitter in JavaScript vor dem JOIN: Jede A/B-Adresse wird in zwei Teilzeilen aufgeteilt, die unabhängig voneinander nachgeschlagen werden. Die Ergebnisse werden als acd_b (zweiter Treffer) und match_quality = "split_both" (beide gefunden) oder "split_partial" (einer gefunden) zusammengeführt.

  • A / in the street column indicates a composite address identifying the same physical location from two streets (corner building or shared driveway).
  • A trailing number in each half of the split is the house number for that half, e.g. Achengasse 4 → street Achengasse, house 4.
  • Both ACDs are valid for the same physical building; the user can choose either.
  • Ein / in der Straßenspalte bezeichnet eine zusammengesetzte Adresse, die denselben physischen Standort von zwei Straßen aus beschreibt (Eckgebäude oder gemeinsame Zufahrt).
  • Eine abschließende Zahl in jeder Hälfte des Splits ist die Hausnummer für diese Hälfte, z. B. Achengasse 4 → Straße Achengasse, Hausnummer 4.
  • Beide ACDs sind für dasselbe physische Gebäude gültig; der Nutzer kann eine davon wählen.

  • Returns both ACDs when both halves resolve, giving the user the full picture for corner parcels.
  • No distance estimation needed — the result is exact if the street+house exists in ADRESSENOGD.

  • Gibt beide ACDs zurück, wenn beide Hälften aufgelöst werden, und liefert dem Nutzer das vollständige Bild für Eckgrundstücke.
  • Keine Abstandsschätzung erforderlich — das Ergebnis ist exakt, wenn Straße + Hausnummer in ADRESSENOGD vorhanden sind.
  • Returning two ACDs (ACD + acd_b) requires the user to inspect both columns for composite matches.
  • Pure Schrebergarten parcel addresses like Parz 38 remain unmatched even after the split because neither half maps to a registered building address.

Status: ACTIVE — implemented in issue #48. For rows still unmatched after Fix A + Fix B, click the “🌐 Try REST API for residual unmatched” button that appears below the results. The page calls the city’s OGDAddressService.svc/GetAddressInfo REST endpoint once per unmatched row. The API performs server-side fuzzy matching and returns the canonical ACD. Concurrency is capped at 8 parallel requests and a maximum of 250 calls per upload session to stay within polite use of the public OGD service. Matched rows receive match_quality = "rest_api_fallback".

Target: ≥ 98% match rate on the 2,039-row test file (up from 94.2% after Fix A + Fix B).

Status: AKTIV — umgesetzt in Issue #48. Für nach Fix A + B noch nicht gefundene Zeilen erscheint unterhalb der Ergebnisse die Schaltfläche „🌐 REST API für verbleibende Adressen versuchen”. Die Seite ruft den städtischen REST-Endpunkt OGDAddressService.svc/GetAddressInfo einmal pro nicht gefundener Zeile auf. Die API führt serverseitig eigenes Fuzzy-Matching durch und gibt die kanonische ACD zurück. Die Parallelität ist auf 8 gleichzeitige Anfragen und maximal 250 Aufrufe pro Sitzung begrenzt. Gefundene Zeilen erhalten match_quality = "rest_api_fallback".

Ziel: ≥ 98 % Trefferquote auf der 2.039-zeiligen Testdatei (gegenüber 94,2 % nach Fix A + B).

  • The city’s OGDAddressService API is publicly available without authentication and is subject to reasonable use; the 250-call session cap stays well within polite limits.
  • Round-trip time is approximately 200–500 ms per request; 8 concurrent requests cap total elapsed time to ≤ 30 s for 118 residual rows.
  • The API’s own matching is more permissive than our static Parquet snapshot for Schrebergarten parcel addresses and edge-case spellings.
  • The city’s JSON response schema is stable: features[0].properties.ACD and features[0].properties.SCD are present when a match is found. The Ranking property indicates the API’s internal match confidence.
  • Users accept that unmatched address fragments (street + house number only, no name or personal data) are sent to the OGD server when they click the button.
  • Der OGDAddressService-Endpunkt der Stadt Wien ist ohne Authentifizierung öffentlich verfügbar und für vernünftige Nutzung ausgelegt; das Sitzungslimit von 250 Aufrufen liegt weit innerhalb fairer Nutzung.
  • Die Roundtrip-Zeit beträgt ca. 200–500 ms pro Anfrage; 8 gleichzeitige Anfragen begrenzen die Gesamtdauer auf ≤ 30 s für 118 verbleibende Zeilen.
  • Das eigene Matching der API ist für Schrebergarten-Parzellenadressen und Sonderfälle großzügiger als unser statischer Parquet-Snapshot.
